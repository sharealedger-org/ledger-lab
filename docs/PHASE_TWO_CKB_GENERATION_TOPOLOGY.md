## Common-key principle

All source records may flow through ordered processes. Only the current key's
required records/state enter the live CKB. Do not load the corpus, a vendor's full
lifetime, a global dependency graph or all scenarios into one JVM. Statistical
recipes are finite state and versioned parameters executed in Scala; Bash wires
processes/partitions and resource gates. Exact downstream financial work remains
in existing or separately gated Scala SJE engines.

## Proposed ordered process topology

| Stage | Common key and order | Inputs / current-key state | Output and required boundary |
|---|---|---|---|
| P0 calibration/reference preparation | Source summary scope, source year, measure, currency | Completed report summaries; small bounded parameter tables; counts and additive statistics | Frozen monetary/distribution parameters, calendar and provenance. Real data that need another grouping require a declared sort. No unsupported fitting from annual totals |
| P1 identity registry and source routing | Typed namespace + stable private party key; aliases/source determining keys have their own explicit order | A party definitions; B known real-VA mappings where included; C identity policy/version. Current mapping row and bounded collision-control state | Persistent artificial-ID map, statuses and routed source instructions. External ID uniqueness/collision checks and separate alias-order sort/merge as needed; no entire population map |
| P2 context generation CKB | Population, scenario, private component, synthetic event date, precedence, stable record ID | A context/recipe definitions; B memberships and selected empirical activity blocks; C routed dated drivers/references. Current component's bounded participants, obligations, counters, parameters and random draws | Coherent event/change instructions for each process/entity plus separate private truth. Definitions/memberships/drivers must actually reach this ordered consumer; the current ordinal recipe loop alone is not proof |
| P3 determining-key assignment merge | Process, source/local determining key, applicable date, precedence, stable ID | A generated instructions; B identity/crosswalk versions; C applicable routing rules | Explicit resolved/ambiguous/missing status with actor/process address. Sort from context order unless already compatible. Missing keys fail or remain deliberately unresolved under policy |
| P4 entity-temporal CKB | Scenario, process, namespace, entity, effective date, precedence, stable ID | A entity seed/history; B resolved event instructions; C routed changes. Current actor/instrument state and next scheduled event; stream the lifetime | Source process records, histories, contractual schedules and controls. Quiet entities receive changes. Master coalescing uses declared entity order; no collecting all vendors |
| P5 source-system and knowledge-time emission | Receiving system/partition plus required local order; separate availability order for cutoff export | Actual source schemas and consumer contracts; bounded output buffers or merge streams | Stable source partitions, early/later evidence views, withheld outcomes. A stage is an ownership/ordering responsibility, not automatically a standalone
JVM or full scan. Compatible adjacent orders may pipe through bounded processes.
An external sort, required grouping change, restart boundary or retained review
partition creates physical work that must be counted. Identity assignment sorts,
external uniqueness and validation scans also count; this is not a two-pass claim.

## Shared dependencies without global memory

A vendor, funding source or market driver may affect many components. Sort the
membership bridge by driver/participant key, stream the relevant version/change
onto each affected membership, then sort those messages into receiving context or
entity order. Do not retain an unbounded reverse index. Common shocks are generated
once at their declared driver/time key and routed consistently. If a result must
feed back to another context, declare an additional ordered round with versioned
messages; do not hide an iterative global simulation in P2.

For large portfolios or components with too many live obligations, use obligation/
instrument keys and explicit aggregation/routing sorts. Fail the participant/state
cap rather than silently split the economic component or retain its whole history.

## Variability and reproducibility

Begin with component/party-specific activity levels, skewed amount weights,
seasonal timing, explicit lifecycle transitions, separate evidence-arrival lags and
a small set of shared drivers. Estimate only parameters supported by observed
inputs; label the others assumptions. Fixed annual envelopes condition the sampled
weights and exact cent allocation; alternative scenarios can vary the envelopes.
Refund/reversal mechanisms and net-versus-gross calibration require explicit rules.
An inactive actor, an unknown identity and an unobserved outcome are distinct.

Random draws derive from seed, stable private key, rule version, date/event and
purpose, independent of source-file order or worker count. Scenario comparisons
may intentionally share base draws under a declared matched-world contract; extra
scenario shocks have explicit identities. Vendor ID allocation must be independent
of mechanisms, relationship groups and numeric source order. Retain the stable
registry and check collision, extension/reordering stability and non-bunching.

Zero-ID observed expenses can inform a separately labeled synthetic attribution
profile when source grain is eligible. Preserve dates/amounts/classifications and
source lineage under declared policies; invented relationships remain invented.
Keep original VA records immutable. Summary-grain receipts stay summary-grain.
Any decomposition needs explicit conservation, lineage and an independent profile.

## Bounds, controls and next falsifier

Proposed initial caps: 64 participants and 64 simultaneous obligations per current
context, 256 current rule/reference versions; stream longer schedules by instrument
key. These are design caps requiring tests, not tested treasury capacities. Reuse
current prototype source-sort guards (100,000 rows AND 32-MiB payload, 16-reader
merge fan-in) where compatible. Template/reference lookup caps remain explicit.
No Spark, Vagrant, Play, Derby or financial Python/Bash substitute.

Record run/process/partition IDs, comparator/version, row/byte conservation,
materialized/pipe boundaries, wall/CPU/RSS high-water marks, buffer/reader peaks,
sort/spill writes, retained/peak sampled disk, calendar/version, distributions,
calibration residuals and actual consumer receipts. Distinguish preparation,
financial compute, orchestration and verification costs. Proposed pipe and retained
profiles must be demonstrated separately before claiming different costs.

Cheapest new falsifier: two operating components share a supplier and a funding
source; one independent component has a misleading overlap; a scheduled funding
receipt is late and partly settles; a reference/role change becomes known later.
Trace it through actual P2/P3/P4 orders, preserving one actor history, coherent
shared shock, cutoff-safe evidence and exact financial controls. Check reordered
inputs/chunk sizes, duplicate/unmatched IDs, same-date ties, state overflow and
source-schema consumption. Expand only after unchanged baseline and this named
fixture pass. Record GenevaERS capability gaps before any measured-support claim.

## Zero-vendor preparation: owner refinement

2026-11-16. A zero vendor identifier is an unresolved/summary bucket, not one
business entity. Assigning synthetic vendors cannot initially use vendor as its
useful CKB break key. Add a dedicated, separately labeled source-preparation path
for eligible unresolved expense records; keep original VA data immutable.

Candidate determining context: canonical agency/fund/object (with an explicitly
versioned object/category grouping where needed). Sort context, synthetic year/
period, effective date and stable source-row identity. The stable context key
excludes year; year/period is a temporal sub-break. Agency alone is a coarse
partition that may conceal very large/diverse groups. Full agency/fund/object is
an initial candidate, not a claim that every group is small. Stream the group's
records and statistics; cap roster/parameter state. Profile actual cardinalities,
largest groups, temporal concentration and scope compatibility before choosing it.

Proposed preparation topology:
1. Classify source grain and eligibility. Separate unresolved supplier expense,
   unsupported aggregate expense and agency-grain receipts; do not manufacture
   vendor attribution for ineligible summaries.
2. Build bounded empirical summaries in agency/fund/object/year order, retaining
   source lineage and per-currency monetary/row controls. Pool/smooth sparse groups
   only under an explicit policy; fund/object reference changes need dated mapping.
3. Prepare a persistent synthetic supplier registry plus many-to-many context
   memberships, independent of ID numerical order. A roster can include recurring,
   occasional and shared suppliers with active intervals. Assignment probabilities
   may depend on category, size, recurrence and time, not identifier proximity.
4. Sort memberships, parameters and eligible source rows into context/time order.
   At the current context CKB stream source records and allocate a simulated supplier
   under the declared recipe. Retain a bounded candidate roster; large memberships
   require another sorted routing/assignment boundary, not an unbounded lookup map.
5. Emit attributed synthetic events with original source locator, synthetic event
   identity, assignment version and observed-versus-invented provenance. Keep a
   deliberate unresolved remainder where specified. Control exact amounts/currency,
   dates and row counts for a pure reassignment profile; decomposition/replication
   has separate explicit conservation and count contracts.
6. Sort by synthetic vendor/effective date/event identity, then consume in the
   entity-temporal source-generation/history process. Only after assignment can
   vendor become the useful common key. The financial SJE path remains unchanged
   unless a separately declared financial behavior is introduced.

Do not equate one context to one vendor or give every agency/fund/object combination
an isolated supplier universe. A stable private registry and sorted membership
bridges allow the same supplier across years, funds, categories and agencies.
Context membership is a generation assumption, not recovered real-vendor truth.
Year-specific roster rebuilding would lose continuity and must not be the default.

Reuse can mean preserving observed year-to-year activity, reusing a supplier
profile or sampling an empirical activity block into a new synthetic year. State
which meaning applies. Repeated blocks get new event IDs and explicitly mapped
dates/availability, source-use lineage, counts and monetary controls. Do not
accidentally duplicate financial events or treat repeated blocks as independent
observations; keep common source ancestry out of future blind train/test splits.

Cheapest falsifier: two years, two context keys sharing one supplier, one seasonal
supplier and one independent background group; include a quiet year and a dated
reference change. Require persistent non-bunched IDs, shared-vendor continuity,
exact source controls, bounded state and correct final vendor/date order. Source
scale and target-runtime support remain separate admission/evidence questions.
