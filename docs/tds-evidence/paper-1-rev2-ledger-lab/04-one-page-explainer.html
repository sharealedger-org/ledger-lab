Ledger Lab: the experiment on one page

State as of 2026-11-12 (Revision 2). Public Virginia purchase order and expenditure data, FY2003 to FY2016.

1. The question

  • A General Ledger (GL) posts business events and keeps totals. The vendor, the order date and the event sequence are thrown away.
  • To answer questions the GL cannot, organisations add more balance tables, sub-ledgers and cubes. Each one must be kept in step with the others.
  • Paper 1 asks about cost: is there a cheaper place to sit, where events are kept in a payments subledger keyed by vendor, and answers are built at query time?
  • Paper 2 asks about learning: can a model trained on posted GL data recover what posting threw away?

2. The cost bowl (Paper 1, Mix graph)

MODEL OUTPUT, not a measurement. The data sizes are measured. The unit rates ($0.02/GB scan, $50 per pair of stores per month) and the query volumes (1,000 annual, 500 sub-annual, 100 dimensional a year) are assumptions.

  • Left wall: keep only events and replay them for every question. Cheap to store, costly to ask.
  • Bottom: a monthly payments subledger keyed by vendor, separate from the general ledger. One row per vendor and month. Questions are answered by joining reference data when asked.
  • Right wall: pre-compute a balance for each anticipated question. Every extra store must be reconciled with the others, so cost climbs with the number of pairs.
  • The depth of the bottom depends on an assumption. If nobody asked sub-annual questions, the annual subledger would be as cheap as the monthly one.

3. What was built and measured

  • A Scala pipeline reads 385 raw files (27.8 GB) and produces balanced journal entries: 224 million rows. Bash only sequences the jobs.
  • From those it posts two ledgers: the payments subledger (10.65 million rows, 1.7 GB) and the general ledger (6.43 million keys).
  • It counts the permutation capacity: how many balances a general ledger would need to hold to answer what the payments subledger answers. The total is 5.0 x 1014, an upper bound.
  • The whole corpus runs on one 4-CPU, 16 GB laptop with a 1 GB heap. Highest process memory was 1.36 GB.
  • Every year balances to zero: 42 of 42 controls pass in each full run. Three full runs were made. Two give identical outputs file for file.

  • Running two years at once saves 27 to 30% of the wall time and costs 5% more CPU. Run alone, one year costs the same CPU as in the baseline (+0.4%), so the extra is lanes competing, not different code.
  • Preparing the data costs about 30 CPU seconds per million rows, steady across all years. Posting does not scale as cleanly, and the reason is not yet tested.
  • The general ledger has about 0.58 keys for every payments subledger row in the years with purchase orders: it is smaller, and it has lost the vendor.

4. Paper 2: what a model can learn

  • Three models get the same tasks. 1: a language model tuned on general ledger records. 2: the same model tuned on payments subledger records. 3: an ordinary structured model on the payments subledger.
  • The gap between 1 and 2 shows what posting lost. The gap between 2 and 3 shows what the language model's prior knowledge costs.
  • A smaller test already predicts which vendors stop trading with the state: C-statistic 0.75, permutation p = 0.001 on held-out years. It is provisional (four training years, simple features).
  • Done so far: plan, text conversion, scoring code, data checks (the general ledger and payments subledger agree to the cent in all 14 years). No model has been trained yet.

6. What is open

  • Run each cost point three times before quoting any cost.
  • Run revaluation and allocation (CCP4, CCP5) on the full corpus.
  • Run the conventional engine on the same data to give the second curve.
  • Decide how net income is defined (the data holds expenditure accounts only), then train and score the three models.
  • Re-run the smaller model tests on the final data.
