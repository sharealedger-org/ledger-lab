## Overview

The Universal Ledger Demo System demonstrates every major financial system pattern using
publicly available data from the State of Virginia (13 years of purchase order and payment
records, fiscal years 2003–2016). The system is implemented in Scala using match-merge
processing — the same algorithmic approach used by GenevaERS for high-volume financial
processing on the mainframe.

The demo is structured as a menu-driven command-line program. Each menu option implements
one canonical financial system pattern. The options are sequenced in dependency order:
each option's outputs become the next option's inputs.

**Public data source:** Virginia Department of Accounts open data portal —
expenditure and revenue files by fiscal year and quarter.

**Engine:** Pure Scala, match-merge (sorted-file join), no Spark required for core processing.
The match-merge approach is the algorithmic heart: sort both files on the same key, read
them in parallel, and merge — producing outputs in a single sequential pass with minimal
memory use. This is the GenevaERS Common Key Buffering principle applied in Scala.

## Data Structures

Four primary data structures flow through the system. All are CSV files.

### Vendor Master (Instrument Master)
The central reference file. One record per vendor.

| Field | Description | Example |
|-------|-------------|---------|
| `instID` | Unique vendor/instrument ID (assigned by option 2) | `1229771` |
| `instEffectDate` | Record effective start date | `2003-01-01` |
| `instEffectEndDate` | Record effective end date | `9999-99-99` |
| `instHolderName` | Vendor name | `1ST CHOICE TECHNOLOGIES` |
| `instTypeID` | Vendor type — `EXP` (expense) or `REV` (revenue) | `EXP` |
| `instVendorAddress` | Street address | |
| `instVendorCity` | City | |
| `instVendorState` | State | |
| `instVendorPostalCode` | ZIP code | |
| `instAuditTrail` | Timestamp of last update | |

### Universal Journal (Standard Journal Entry / SJE)
One record per transaction line. Every financial event — whether received as input or
generated by the system — writes an SJE to the audit trail. Any balance can be
reconstructed by summing all SJEs for that balance key.

| Field | Description | Example |
|-------|-------------|---------|
| `transJrnlID` | Journal ID | `ID12003/03/01` |
| `transJrnlLineID` | Line number within journal (1=debit, 2=credit) | `1` |
| `transLegalEntityID` | Agency code (legal entity) | `101` |
| `transCenterID` | Fund code | `0100` |
| `transProjectID` | Object code | `1001` |
| `transNominalAccountID` | Nominal account — balance bucket designator | `EXP202` |
| `transTransAmount` | Transaction amount | `284.27` |
| `transFiscalPeriod` | Fiscal year/quarter | `03` |
| `transAcctDate` | Accounting date | `2003/03/01` |
| `transCurrencyCodeSourceID` | Source currency | `USD` |
| `transCurrencyCodeTargetID` | Target/book currency | `USD` |
| `transDirVsOffsetFlg` | Direct (`D`) or offset/contra (`O`) | `D` |
| `transAdjustFlg` | Adjustment flag | `N` |

### Universal Balance (Ledger)
One record per unique combination of (Vendor ID × Nominal Account × Fiscal Period ×
currency pair × other chartfields). The balance is the accumulated sum of all SJEs
for that combination. Updated each run cycle.

Key fields mirror the SJE fields, plus:
- `ldgrTransAmount` — accumulated balance (sum of all SJEs for this key)
- `ldgrLdgrlID` — unique balance record ID

### Vendor Update (Instrument Master Update)
Used only by the Arrangement Reclass process (option 9). Contains new versions of
Vendor Master records where the `instTypeID` has changed since the last run — the
reclass trigger.

| Field | Description |
|-------|-------------|
| `instID` | Vendor ID (matches Vendor Master) |
| `instTypeID` | New type (`EXP` → `REV` or `REV` → `EXP`) |
| `instEffectDate` | Effective date of the change |

### Reference Tables
Small lookup tables used by currency and aggregation processes:
- **Agency (Legal Entity) table** — agency code → agency name, base currency
- **Fund table** — fund code → fund description
- **Object table** — object code → object description
- **Program table** — program code → program description
- **Currency Exchange Rate table** — (currency pair, date) → exchange rate
- **Historical Processing table** — prior processing dates for revaluation walk-forward

## Order of Processing

The menu options are sequenced by data dependency. Options 1–3 must run before
options 4–9. Within options 4–9, the correct production order is:

```
1. Transaction Capture (option 1) — raw data → matched PO/payment records
2. Standardize & Journalize (option 2) — matched records → Vendor Master + SJEs
3. Posting (option 3) — SJEs → Balances
4. Arrangement Reclass (option 9) — must run before revaluation
5. Currency Conversion (embedded in option 3 / option 5)
6. Currency Revaluation (option 5 — partial)
7. Currency Revaluation Walk-Forward (option 5 — backdated case)
8. Contra Creation (option 4 — Reconciliation) — must run last, after all balances updated
9. Data Aggregation (option 5) — reporting views from final balances
10. Financial Allocation (option 6) — from final balances
11. Consolidation & Elimination (option 7) — from final balances
12. Forecasting & Budgeting (option 8) — from final balances
```

### Option 1 — Transaction Capture and Adjustment
**FSP Pattern:** Transaction Capture & Adjustment  
**Implementation:** `poToPayMatch.scala` ✅ Complete

**What it does:**  
Reads raw Virginia expenditure files (quarterly, by fiscal year) and purchase order
files. Joins payments to POs by vendor name, agency, and amount. Enriches with
reference data (Agency, Fund, Object, Program tables). Writes a combined
denormalized output file ready for standardization.

**Inputs:**
- `payment/FY{yy}q{q}exp.txt` — quarterly expenditure files (tab-delimited)
- `poData/VA_opendata_FY20{yy}.txt` — annual PO file (tab-delimited)
- `common/aRefAgencyTab.txt`, `aRefFundCSV.txt`, `aRefObjectCSV.txt`, `aRefProgramCSV.txt`

**Outputs:**
- `20{yy}_Combined_Pay_PO/` — joined payment+PO+reference records (CSV)

**Coding with Kip episode content:**
- Show the raw VA expenditure file structure — what a government payment record looks like
- Show the join logic: how vendor name + agency + amount creates a match
- Demonstrate running the script, show record counts before and after
- Discuss: why match-merge vs. hash join — what the sort order buys you
- Show the enriched output: a single record with vendor name, fund description,
  object description, amount, date

### Option 2 — Standardize and Journalize
**FSP Pattern:** Standardize & Journalize
**Implementation:** `standardizeAndSort.scala` ✅ Complete (supersedes `transStandardize.scala` + `sortJE.scala`)

**What it does:**  
Reads the combined payment records and produces two outputs:
(a) a Vendor Master table with a unique instrument ID assigned to each vendor, and
(b) Universal Journal entries (SJEs) — two lines per transaction (debit + credit offset
to cash). Expense payments produce `EXP{prog}` nominal accounts; revenue records
produce `REV{src}` nominal accounts. Aggregates by (Agency, Fund, Object, Program, Date)
before journalizing to reduce volume.

**Inputs:**
- `FileList.csv` — manifest of all files to process (filename, type, format, year, quarter)
- Raw VA expenditure files referenced in the manifest

**Outputs:**
- `JE{filename}.csv` — sorted Universal Journal files, one per input file
- `SortedJE{year}.csv` — journals sorted on full balance key, ready for posting

**Coding with Kip episode content:**
- Show the FileList manifest — how the system knows what to process
- Explain double-entry: why every transaction creates two journal lines
- Show an expense record becoming `EXP202` and a revenue record becoming `REV{src}`
- Explain the nominal account as the balance bucket designator — the key insight
- Show the Vendor Master being built: each unique vendor name gets an ID
- Demonstrate the sort step: why sorted order is required before posting

### Option 3 — Posting
**FSP Pattern:** Posting  
**Implementation:** `post.scala` ✅ Complete

**What it does:**  
The core financial loop. Reads sorted SJE files and existing Balance (Ledger) files
in parallel. Uses match-merge to accumulate SJE amounts into the correct balance
record for each unique key combination. Writes updated balances. If no balance
exists for an SJE key, creates a new balance record. If the balance file doesn't
exist yet (first run), creates it.

The balance file becomes the input for the next run cycle — incremental posting.
Every balance can be reconstructed from its SJE history at any time.

**Inputs:**
- `SortedJE{year}.csv` — sorted Universal Journals (all files for the year)
- `LDGR{year}.csv` — existing balance file (or absent on first run)

**Outputs:**
- `LDGR{year}.csv` — updated balance file (overwrites input via temp rename)

**The match-merge loop (the algorithmic heart):**
```
while journals or balances remain:
  if journal key == balance key → accumulate journal amount into balance
  if journal key <  balance key → new balance from journal; handle read-ahead swap
  if journal key >  balance key → write balance; advance balance
```

**Coding with Kip episode content:**
- Show the sorted journal file and the existing balance file side by side
- Walk through the match-merge logic step by step — the three cases
- Demonstrate creating a new balance when none exists (first run for a key)
- Show control totals: journals read, balances read, balances written
- Run for one year; show the resulting balance file
- Explain the incremental model: run again next quarter, only new SJEs needed

### Option 4 — Reconciliation (Contra Creation)
**FSP Pattern:** Reconciliation  
**Implementation:** `contraCreation.scala` ✅ Complete

**What it does:**  
Creates contra (offsetting) transactions that, when posted to the balance file,
cause the entire file to sum to zero. This is the reconciliation proof: after contra
posting, if the file does not sum to zero, an error exists.

The contra transaction is a summary record — it does not include the Vendor ID
or Balance ID fields. It represents the total of all vendor balances, negated,
aggregated at the Legal Entity (Agency) × Nominal Account level.

**This must run last** — after all other processes (including Arrangement Reclass
and Currency processes) have updated balances for the current cycle.

**Process:**
1. Read all balance records in a single pass
2. Accumulate total amount by (Legal Entity, Nominal Account, Currency pair, Fiscal Period)
3. For each accumulated total: create a contra SJE with amount × -1, no Vendor ID, no Balance ID
4. Write all contra SJEs to the SJE audit trail file
5. Post contra SJEs to corresponding contra balance records
6. Verify: sum of all balances (vendor-level + contra) = 0

**Inputs:**
- `LDGR{year}.csv` — final updated balance file for the cycle

**Outputs:**
- `CONTRA_SJE{year}.csv` — contra journal entries
- `LDGR{year}.csv` — updated with contra balance records appended

**Coding with Kip episode content:**
- Show a set of vendor balances before contra creation
- Explain why subledger balances must equal GL balances — what breaks if they don't
- Walk through the aggregation: collapsing vendor detail to agency/account summary
- Show the contra transaction created: same fields, negated amount, no vendor ID
- Run the process; verify the file sums to zero
- Discuss: this is the foundation of double-entry bookkeeping — every debit has a credit

### Option 5 — Data Aggregation
**FSP Pattern:** Subledgers / Aggregation
**Implementation:** `dataAggregation.scala` ✅ Complete (ViewSpec-driven; see vlog E130 for original spec)

**What it does:**  
Produces analytical views from the posted balance file. Loads balance data into
memory (by year) and produces three output tables:

1. **Top-N vendors by spend** — vendor ID, name, total spend; sorted descending
2. **Detail balance table** — all balances at vendor × nominal account level with
   full vendor attributes joined in
3. **Summary balance table** — balances without vendor dimension; aggregated by
   (Agency, Fund, Object, Program, Nominal Account, Fiscal Period)

The summary table is the GL-equivalent view; the detail table is the subledger view.
Reconciliation between them (they must agree on every aggregate key) demonstrates
the contra proof from option 4.

**Inputs:**
- `LDGR{year}.csv` — final balance file
- `VendorMaster.csv` — for name enrichment on detail table

**Outputs:**
- `TOP50_{year}.csv` — top vendors by spend
- `DETAIL_BAL_{year}.csv` — vendor-level balances with attributes
- `SUMMARY_BAL_{year}.csv` — GL-level summary without vendor dimension

**Coding with Kip episode content:**
- Show the interactive menu: how many years to load, which year to analyze
- Demonstrate the top-50 vendor output — "here are the biggest spenders"
- Show the trial balance by legal entity (agency) — debits = credits
- Show the detail vs. summary reconciliation: subledger total = GL total
- Discuss: this is the foundation for BI/reporting — the same data, different grain

### Option 6 — Financial Allocation
**FSP Pattern:** Financial Allocation  
**Implementation:** `financialAllocation.scala` ✅ Complete

**What it does:**  
Takes a balance (typically an overhead or shared cost balance) and distributes it
across a set of cost objects using an allocation rule. Each allocation produces
a set of new SJEs: debits to the receiving cost objects, credit to the source balance.

Allocation in the VA data context: distribute shared agency overhead (e.g., executive
office costs coded to a single program) across all programs in that agency, weighted
by each program's share of total expenditure.

**Process:**
1. Identify source balances to allocate (by nominal account or program code)
2. Identify receiving cost objects (programs in same agency)
3. Calculate each receiver's weight (receiver spend / total spend)
4. Generate allocation SJEs: debit each receiver × (source amount × weight),
   credit source × -1 (zeroing the source balance)
5. Write allocation SJEs to audit trail; post to balances

**Inputs:**
- `LDGR{year}.csv` — posted balance file
- Allocation rule table (configurable): source account, driver, receiver pool

**Outputs:**
- `ALLOC_SJE{year}.csv` — allocation journal entries
- `LDGR{year}.csv` — updated with allocation results

**Coding with Kip episode content:**
- Show a shared cost balance before allocation
- Walk through the weight calculation: each program's share
- Show the SJEs generated: one debit per receiver, one credit to source
- Run the allocation; show the source balance zeroed, receivers increased
- Discuss: allocation is the reverse of aggregation — it explodes a summary into detail
- Show: the total doesn't change, just the distribution

### Option 7 — Consolidation and Elimination
**FSP Pattern:** Consolidation & Elimination  
**Implementation:** `consolidation.scala` ✅ Complete

**What it does:**  
Combines balance files from multiple legal entities (agencies) into a single
consolidated view, then eliminates interagency transactions so that
intergovernmental transfers don't double-count.

In the VA data: multiple agencies transact with each other (transfers between
agencies, shared service charges). When consolidating to a state-wide total,
these interagency amounts must be eliminated — otherwise both the paying agency's
expense and the receiving agency's revenue are counted, inflating both totals.

**Process:**
1. Read balance files for all agencies (legal entities)
2. Combine into a single consolidated balance file
3. Identify interagency pairs: (Agency A expense to Agency B) paired with
   (Agency B revenue from Agency A) — matched on transfer code and amount
4. Generate elimination SJEs: debit Agency B revenue, credit Agency A expense
5. Write elimination SJEs; post to consolidated balances
6. Verify: all interagency pairs net to zero in consolidated view

**Inputs:**
- `LDGR{year}.csv` files for each agency (or partitioned by agency)
- Interagency transfer identification table (agency pair + transfer nominal account)

**Outputs:**
- `CONSOL_LDGR{year}.csv` — consolidated balance file
- `ELIM_SJE{year}.csv` — elimination journal entries

**Coding with Kip episode content:**
- Show two agency balance files with matching interagency transfers
- Demonstrate consolidation: stacking the files
- Show the double-counting problem: same dollar appears as both expense and revenue
- Walk through elimination: the matching logic, the SJEs generated
- Show the consolidated view after elimination: interagency amounts zero out
- Discuss: this is how governments and corporations produce group-level financials

### Option 8 — Forecasting and Budgeting
**FSP Pattern:** Forecasting & Budgeting  
**Implementation:** `forecastingBudgeting.scala` ✅ Complete

**What it does:**  
Creates a budget/forecast version of the balance file alongside the actuals. For
each balance in the actuals, generates a budget balance using a simple projection
rule (e.g., prior year × growth factor, or user-supplied amounts). Produces
variance reports: actual vs. budget by agency, fund, program, and nominal account.

**Process:**
1. Read actuals balance file for a base year
2. Apply projection rules to generate budget balances for the forecast year
3. Write budget balance file (same structure as actuals, with `BUDGET` book code)
4. Produce variance output: actual amount, budget amount, variance, variance %

**Inputs:**
- `LDGR{base_year}.csv` — actuals for the base year
- Projection rule table (account, growth factor or fixed amount)

**Outputs:**
- `BUDGET_LDGR{year}.csv` — budget balance file
- `VARIANCE_{year}.csv` — actual vs. budget variance report

**Coding with Kip episode content:**
- Show the actuals balance file for a base year
- Apply a simple growth rule: "inflate all EXP accounts by 3%"
- Show the budget balance file generated
- Produce the variance report: which agencies are over/under budget
- Discuss: forecasting works at the balance level, not the transaction level —
  this is why keeping the balance file is essential
- Show: changing the growth factor and re-running — instant new forecast

### Option 9 — Financial Modeling (Arrangement Reclass)
**FSP Pattern:** Modeling  
**Implementation:** `arrangementReclass.scala` ✅ Complete

**What it does:**  
The most complex process. When a Vendor Master record changes in a way that affects
how balances are classified, reclassification transactions must be generated to move
existing balances from the old classification to the new one — including for all
prior periods affected by the change.

In the VA data: when a vendor's `instTypeID` changes from `EXP` to `REV` (or vice
versa), all existing balances for that vendor must move from `EXP{nnn}` nominal
accounts to `REV{nnn}` accounts. If the change is backdated, this must happen for
every affected accounting period.

**Process:**
1. Read Vendor Update file (vendors whose type has changed since last run)
2. For each changed vendor: read all current balance records for that vendor
3. For each balance record: generate two SJEs —
   - Credit the old nominal account (e.g., `EXP202`) × -1 (reversing the old balance)
   - Debit the new nominal account (e.g., `REV202`) × +1 (opening the new balance)
4. If the effective date of the change is backdated: generate reclass SJEs for each
   affected fiscal period back to the effective date
5. Write all reclass SJEs to audit trail; post to balances
6. Update Vendor Master with new type and effective date

**Key rule:** Arrangement Reclass must run **before** Currency Revaluation in the
processing cycle — because revaluation processes can also spawn multiple transactions
per affected period, and the multiplying effect between reclass and revaluation
means reclass must fire first to establish the correct balance structure.

**Inputs:**
- `VendorUpdate.csv` — vendors with changed type since last run
- `VendorMaster.csv` — current vendor master
- `LDGR{year}.csv` — current balance file (all years affected by backdated changes)

**Outputs:**
- `RECLASS_SJE.csv` — reclassification journal entries
- `LDGR{year}.csv` — updated balance files for all affected years
- `VendorMaster.csv` — updated with new type and effective dates

**Coding with Kip episode content:**
- Show a vendor with type `EXP` and its current balances (`EXP202`, `EXP405`, etc.)
- Show the Vendor Update record: type changing to `REV`
- Walk through the SJEs generated: one credit/debit pair per balance record
- Run the process; show the old `EXP` balances zeroed, new `REV` balances created
- Demonstrate backdating: change effective date to prior year; show multi-period SJEs
- Discuss: this is why the SJE audit trail matters — every balance change is traceable
- Show: the total financial position doesn't change, only the classification

## Implementation Notes for Developers

### Scala Idioms Used in This Codebase
- All file I/O uses `scala.io.Source` and `java.io.PrintWriter` — no Spark, no JDBC
- Match-merge pattern: `BufferedIterator` with `hasNext` / `next` — see `post.scala`
- Record types are Scala `case class` — see `datatypes/Ledger.scala`, `Transaction.scala`
- "High values" sentinel for EOF: `"𝖛" * key.length` — triggers write-out of remaining records
- Control totals printed at start and end of every module

### Adding a New Option
1. Create a new `object` in `org.universalledger.foundation.va.ledger/` following the pattern of `post.scala`
2. Add a `case` branch in `LedgerApp.scala` dispatch
3. Follow the header comment convention (program name, purpose, author, date, change log)
4. Print control totals: records read, records written, start time, end time

### Running the System
```bash
cd 02-foundation/va_pipeline
sbt run
# Follow menu prompts for input/output paths and year/quarter
```

Data paths default to `/VAdata/data/` inside the Vagrant VM. Override at the menu prompt.

## Relationship to GenevaERS

The match-merge algorithm in `post.scala` is the pure-Scala expression of GenevaERS
Common Key Buffering (CKB). GenevaERS implements the same pattern in compiled machine
code on z/OS — the difference is performance scale (millions of records/minute vs.
hundreds of thousands), not algorithmic approach.

The VA Demo System is therefore a pedagogically transparent version of what GenevaERS
does in production: one pass through sorted data, resolving multiple processes against
the same record, writing outputs directly. Understanding this system is a prerequisite
to understanding why GenevaERS performs the way it does.
