**Bob's refinements to item 5, for the owner to accept or reject:**
- **Two numbers per system:** the *cold total* (the whole Phase 1 + Phase 2 set run from scratch) and the *marginal cost* of the new capabilities when Phase 1 outputs exist. One number would hide an index-heavy system that looks cheap incrementally and expensive from scratch.
- **The cost of a capability is its incremental cost (owner, 2026-11-13).** "Files read" is the wrong measure: a CKB pass can carry more capabilities without added overhead, so a new view or engine riding an existing ordered stream reads nothing more. Measure, per added capability and per system: **incremental physical passes and incremental input rows and bytes scanned** (the manifest fields `input_rows`, `input_bytes`, `physical_pass_count`, `sort_count`, in `docs/MEASUREMENT_AND_LOGGING.md`), plus incremental elapsed time, CPU, per-process peak memory, output rows and bytes, retained storage, and reconciliation. A capability that needs a **new sort order** adds a pass and a sort (`02-foundation/README.md`); one that does not, should not. On the control, the equivalent is added index builds, queries, rebuilds and database bytes. A **common I/O counter** for both systems is still to be chosen, because the CKB's logged input bytes and the control's SQLite page reads are not the same thing. Total elapsed time for the whole set stays the headline number; the incremental measures explain it. Open point to settle with the measured data: `docs/COST_GRAPH_DESIGN.md` says CCP3 to CCP5 are produced "in the same pass" (line 231) and also "one more bounded pass over movement rows" (line 219); `physical_pass_count` from the runs decides which.

- **The x-axis is capabilities added**, not materialization level. Name this graph separately from the Engine and Process graphs.
- **Phase 1 must still reconcile after every change.** The Phase 1 control totals and gold hashes (CKB: `MANIFEST.csv`, `MANIFEST_SJE.csv`; control: W1 debit = credit and the W2/W3/W4 commitment totals) stay identical. If a number moves, log it as a change of definition, not a clean addition.
- **Existing measurement rules apply:** keep orchestration, engine compute, storage, sorting and reconciliation separately identifiable; record physical passes and per-process memory high-water marks; count any rebuild a change forces (for example a schema or index change on the control).
- **Phase 1 caveats carry over:** the timed-scope and population differences (baseline record section 3) are reconciled first. **Hardware is the same class: both Phase 1 runs, CKB and control, were on Intel Macs with 16 GB and four logical threads (owner, 2026-11-12; baseline record section 3). The M1 Mac is only where Bob's later sessions ran.** The companion runs do not record the CPU model, and the control host has two physical cores; state both when citing. Phase 1 results were single runs with no repeatability claim, so Phase 2 needs replicate runs.
